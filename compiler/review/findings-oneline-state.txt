Reviewer findings: a one-line state and init
Question: does every behaviour that is correct on the target stay correct on this branch?

Why. The old output was wrong. `state { x: Nat }` and `init { x := 0 }` close on the header line. The line walker started on the next line, so both lists were empty. A field declaration and an assignment were dropped.

Probe:

```
speck A {
    state { x: Nat }
    init { x := 0 }
}
```

Target compiler (the header-line close) stored `state` variables `[]` and `init` assignments `[]`. Working compiler stores variable `x` and assignment `x := 0`.

Example output does not change, so the output pin stays sha256 4d432ac8c74e6ad7371ac85d09f0266acd7e76cc9ae971b9ad858e8ee41f7c2a. It was not updated. No example uses a one-line state.

Limits. `state { }` and `init { }` store empty lists. A comment after the closing brace is ignored, and the field is still stored. A `}` that sits inside `//` does not close the speck: `state { x: Nat // note }` is `missing final "}"` at column 9 of the speck header. A nested `box: { a: Nat, b: Nat }` is one record field. A `//` on its own line inside a multi-line state does not drop the next field. A comma in `state { x: Nat, y: Nat }` stays inside the type and does not start a second field. `init { x := 0, y := 1 }` stores both assignments.

`compiler/src/__tests__/oneline-state-edges.test.ts` pins the empty before-value and the after-value.
