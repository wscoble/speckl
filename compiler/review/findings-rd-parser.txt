Reviewer findings: recursive-descent parser vs the output-hash branch
Question: does every behaviour that is correct on the target stay correct on this branch?

Mechanical equivalence, IR. `compiler/src/__tests__/walker-vs-rd.test.ts` runs the output-hash line walker (the copy in `compiler/src/__tests__/line-walker/`) and `parseSpeckDocument` on every `examples/*.speckdl` file and every `.speckdl` fixture under `compiler/src/__tests__/fixtures` and `compiler/__tests__/fixtures`. Both ASTs go through the same `lower()` with `resolveImports: false`. `JSON.stringify` of the two IR values is equal for all 22 files, including `KafkaKRaft.speckdl` and `OAuth2AuthorizationCode.speckdl`. An empty file and a comment-only file also lower to the same IR.

Malformed input is not the same program. The line walker accepts a missing final `}`, an extra `}`, text after `}`, an unrecognized member, and `§`, and returns an AST. This parser rejects those and names the line and column: missing `}` at `bad.speckdl:1` column 9, extra `}` at line 3 column 1, text after `}` at line 2 column 3, unrecognized member at line 2 column 5, `§` at line 2 column 2. An unterminated string is `Parse error at bad.speckdl:2: unterminated string` from the walker and the same text plus ` (column 8)` from this parser. `speck` with the name on the next line is `Parse error at bad.speckdl:1: speck name must be on the same line as "speck"` from both, with no column.

Output hash. The target compiler is the output-hash branch. The working compiler is this branch. Both hash every `examples/*.speckdl` file at `-t all` and `-t all-ir` to the same sha256:

9bdc5a8a21f64044b1200534581f67a08a8fb8aea206cdb61c365a8b1ca18bc1

That constant is `OUTPUT_SHA256` in `compiler/src/__tests__/compile-pipeline.test.ts` on the target branch and on this branch. The test builds one map. Each example is its own key, `<file> -t all` and `<file> -t all-ir`, and the value is that run's file digests. The hash is sha256 of `JSON.stringify` of the whole map. One changed example moves the hash. The hash did not move, so every example's output is identical, not only the combined digest. The output-hash pin is unchanged on purpose.

`parseSpeck` calls `parseSpeckDocument` in `compiler/src/rd-parser.ts`, which calls the token lexer. `compiler/src/__tests__/parser-intended-diff.test.ts` checks the shapes a later change will fix, and they still match the line walker.

Fail closed. `compiler/src/__tests__/parser-malformed.test.ts` checks the position, not only the wording. A missing `}` is `missing final "}"` on the opening brace's line and column. An extra `}` is `extra "}"` on that brace. Text after a close is `text after a speck's "}"` at that text. An unrecognized member names the line and column. An unterminated string names the opening quote. A `}` inside a string is not an extra close. File-level `import` is syntax-checked and not resolved. Go still drops an `else if`, a nested `if`, a `for` inside an `if`, and a `require` inside an `if`.

The README, SPEC, and CHANGELOG describe this parser. That text does not itself change compiled output.
