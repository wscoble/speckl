# v0.4 Claims Layer Work Order

> Source context: `docs/claims-dossier.md`. Read it first. It is the
> canonical design record. This file gives the build tasks, file locations,
> and acceptance criteria. Do not force-push main. `npm run verify` (the Z3
> suite) must stay green at every step.

The primitive set, the block syntax, the claims surface, and the verdict
lattice are defined in the dossier, sections 2.1 through 2.4. This file uses
that set and that syntax. It does not define a second list.

## Sequencing

A token-based recursive-descent parser rewrite is pending. Its lineage is
branch `cursor/speckl-brace-scan-main-fb9b`
([PR #53](https://github.com/wscoble/speckl/pull/53)), the comment- and
string-aware brace scan. The rewrite is not merged. Tasks that touch the
parser, or that depend on members the parser does not accept yet, land after
that rewrite merges.

Each task is its own pull request, stacked on the previous one.

These do not depend on the parser, so they can land first:

- **Task 3** — the resolver registry. Interface, registry, the `filesystem`
  and `static-manifest` backends, and the out-of-tree plug-in point. Not
  wired into the parser or the IR.
- **Task 6, ledger schema only** — the append-only incident record shape.
  The replay generator, `speckl-incidents --check`, and the near-miss budget
  use `covers` and generated monitors, so that rest of Task 6 waits.

These land after the rewrite merges, one stacked pull request each, in this
order: Task 1, Task 2, Task 4, Task 5, the rest of Task 6, Task 7. The
`speckdl/SPEC.md` v0.4 section lands with Task 1, because it documents
members the compiler does not accept until that task.

## Ground rules

- Pluggability is a hard constraint (dossier section 8). Observability and
  data-source integrations stay modular generator targets and resolvers.
  Nothing in a claims pass hardcodes a backend.
- One IR, two front-ends. The claims surface is a parser front-end. It lowers
  to the same IR as the block form (dossier section 2.3).
- Every new pass ships with its own tests, and with at least one example spec
  under `examples/` exercising it.
- Worked examples use the fictional ExampleCo story in dossier section 4.
  They do not name a real customer or a real incident.

## Canonical primitives

Task 1 and Task 7 both implement this set, from dossier section 2.1:

`claim`, `evidence`, `provenance`, `ensured`, `except`, `root`, `coupling`,
`layer`, `verdict-cap`, `commit`, `covers`.

`verify` stays the v0.3 verification block. `compose` is not a primitive;
`commit` is the composition member. `horizon` is a field of `layer`.
`incident` is a ledger record, not a spec member.

## Task 1 — New member types (parser + IR)

Add to the brace grammar and the IR (lowering and typing). The block form is
the canonical syntax. Shapes:

- `claim <Name>[(args)][: fact|obligation|capability] { <members> }`
  Members inside the claim: `evidence &<id>`, `provenance &<id>`,
  `ensured &<id>`, `except <condition> -> <consequence>`,
  `coupling <Term> at <Layer>`, `covers &<id>`, `verdict-cap <Verdict>`.
  `verdict-cap` is a claim member. It is not a suffix on `coupling`.
- `root <Name> { authority <text>, basis <text>, trust <Verdict> }` —
  terminal, zero evidence. `trust` is required. The four verdicts and the
  total order are dossier section 2.4.
- `commit <Name> { claims: <Name> and <Name> ... }` — composition. Bare names
  are internal claim references.
- `layer <Name> { horizon &<id> }` — the horizon is a record reference, not
  a literal, wherever the deployment provides one. The layer name `global`
  is reserved: a coupling `at global` forces verdict ceiling `Corrected`.
- Top-level `provenance { }` (PROV-O clauses, already in the grammar) is a
  different production from `provenance &<id>` inside a claim. Both survive.

Acceptance:

- The parser round-trips every new member. The IR records each one in the
  facets sketched in dossier section 2.3. The printer preserves them.
- `examples/greybeard/ops-claims.speckdl` (Task 4) parses. Its incidents are
  the fictional ExampleCo set from dossier section 4.

## Task 2 — Compiler validation passes (additive)

These passes read the members from Task 1. They land after the parser
rewrite.

1. **Graph validation.** The provenance/support graph is finite and acyclic.
   A non-root claim chains to a root. A cycle or a rootless chain is a
   compile error with a precise span.
2. **Resolvability.** `evidence &id`, `covers &id`, and horizon references
   are checked against the resolver registry (Task 3). An unresolvable
   pointer is a type error at the cheap rung. Diagnostics distinguish parse,
   resolve, and semantic failures.
3. **Verdict lattice.** Use the total order and the `trust` member from
   dossier section 2.4. Enforce:
   - `derived ≤ min(claim premises) ≤ trust(root)`, or `derived ≤ trust(root)`
     when the only support is the root. `min` is the minimum of that total
     order.
   - A coupling `at global` forces ceiling `Corrected`. A declared
     `verdict-cap` may tighten the effective cap and may not raise it.
   - A missing `trust` on a root is a compile error.
4. **Claims cannot invent instrumentation.** An evidence pointer that maps
   to no registered measurement class is a compile error naming the missing
   instrument.

Acceptance: negative tests for each failure mode (cycle, rootless,
unresolvable, cap violation, missing `trust`, missing instrument) with the
diagnostic class in the message.

## Task 3 — Resolver registry (service interface)

This task does not depend on the parser. It does not modify the parser or
the IR.

- Define a resolver SPI (an interface plus a registry) in the compiler. A
  backend answers two queries: existence (compile-time) and shape/lookup
  (runtime).
- Ship two reference backends. `filesystem` reads Markdown records with YAML
  frontmatter. `static-manifest` reads a JSON object mapping record ids to
  measurement classes.
- Document the plug-in point: an out-of-tree backend implements the same
  interface and registers itself on the registry. Put the SPI at
  `compiler/src/resolver/index.ts` and export it from the package as
  `speckl/resolver`, so an external backend can depend on an install of this
  package. This repository does not load backends by package name or by
  network. A Greybeard Core resolver adapter, if any, lives out of tree and
  uses that plug-in point. There is no in-tree Greybeard adapter and no
  feature flag that imports one.

Acceptance: tests run offline on `static-manifest`, with no network and no
dependency on a Greybeard service. The tests cover an unknown id, a malformed
manifest, and a backend that throws, along with the successful queries. A
reader can add a backend outside this tree from the documented plug-in point
alone.

## Task 4 — Worked examples

1. `examples/greybeard/ops-claims.speckdl` — the SRE surface from dossier
   section 4, written with the fictional ExampleCo sync. Coupling terms are
   local, upstream, vendor-api, and wan. The wan term is `at global` and the
   claim's `verdict-cap` is `Corrected`. The four fictional records are
   static-manifest entries: mirror-host 404 (upstream), PebbleKV (vendor-api),
   Quill unconfigured with no root (configuration), and the Keepsake tombstone
   (lifecycle, not an incident). The spec carries a `covers` edge for
   `incident/exampleco-mirror-404`.
2. `examples/claims/exampleco-backup.speckdl` — the `BackupWithinRTO` claim:
   root, `trust`, obligation type, `except` boundary, and `commit`
   composition, as in dossier section 2.2.

Acceptance: both compile under `npm run verify`. SMT output for `ensured`
invariants passes the Z3 suite. A verdict-cap diagnostic is demonstrable on
a claim that couples `at global` and declares `verdict-cap Verified`.

## Task 5 — Generator targets (pluggable observability)

New generator modules, registered the same way as the existing targets:

- `prometheus.ts` — ensured windows and thresholds become SLO and burn-rate
  alert rules. `except` boundaries become inhibit / maintenance-window rules.
- `grafana.ts` — one panel per coupling term (term-indexed observability)
  plus a verdict ledger dashboard.
- `otel.ts` — evidence pointers become recording and query config stubs.
- `resolver-manifest.ts` — emits the measurement-class manifest from claims
  (the requirements document for observability).
- `receipt.ts` — provenance graph plus verdict history become an audit
  receipt. Extend the existing provenance / CycloneDX machinery.

Acceptance: each target is independently selectable via the existing
`--target` style of flag. No target imports another target's internals.
Adding a target means editing the registry and adding the new module.
Snapshot tests cover generated output for the two worked examples. An
implementation generated from a claim produces its probe too.

## Task 6 — Incident ledger runtime skeleton

Ledger schema, which can land before the parser rewrite:

```
{
  id, awake_term, attributions, violated_commit,
  evidence_refs[], response, verdict_history[]
}
```

The rest waits on Task 1, because it cites `covers` and generated monitors:

- Incident-to-replay generator. The scaffold mocks the awake term at the
  boundary, drives the generated monitor for the violated commit, and asserts
  semantic outcomes (detection, attribution, verdict).
- CI gate `speckl-incidents --check`. It fails when an incident in the
  manifest has no `covers` edge in any spec revision. It does not look at
  coupling terms.
- Near-miss versus incident, with separate budget accounting. The Keepsake
  tombstone in dossier section 4 is the lifecycle case: it is not an incident
  and it is not a near-miss.

Acceptance:

- A replay test generated from the fictional ops-claims incidents passes
  against the current spec.
- With the `covers` edge for `incident/exampleco-mirror-404` present,
  `speckl-incidents --check` succeeds.
- Deleting that `covers` edge makes `speckl-incidents --check` fail.
- Deleting a coupling term does not make `--check` fail. Coupling is a
  Task 2 concern.

## Task 7 — Claims surface front-end (second parser)

- The condensed form in dossier section 2.3: indentation-scoped, breadth-first,
  `&` for external refs, `*` for internal refs, `and` for conjunction, `&`
  reserved for pointing.
- Lowers to the same IR as the block form. The parity rule: a claims-surface
  file and the equivalent block-form file produce identical IR.
- The primitive set is the eleven names in "Canonical primitives" above.

Acceptance: parity tests against the block form on the two worked examples.
A smoke "reasoning replay" fixture uses the surface as a scratchpad trace
(parsed and lowered, not executed) and documents the four-arm evaluation
protocol from dossier section 7 for a later run.
